## 1. 问题

<!-- 为什么要做这个需求。回答"值不值得做"
  - 3 要素，每要素 1-2 句: 用户痛点（具体困难）、影响范围（多少人/多频繁）、为什么现在做（触发事件）
  - EXCLUDE: 技术实现原因、内部架构限制 -->

AI agent 执行复杂任务时容易跑偏：自由发挥导致方向偏离、过程不可见、质量不可控。所有使用 AI agent 做工程任务的开发者每天都面临这个问题。当前只能靠人工盯着（不可规模化）或事后修复（成本高），需要一个在执行过程中施加约束的引擎。

## 2. 目标用户

<!-- 给谁做。回答"谁会用"
  - 用户角色 + 使用场景 + 当前替代方案及其不足
  - EXCLUDE: 系统内部组件名、数据模型 -->

使用 AI agent 完成软件工程任务的开发者。典型场景：用 agent 实现功能（容易跑偏）、大任务拆分执行（中间无法检查）、简单 bug 修复（完整流程太重但不走又没保障）。当前替代方案是人工监督（注意力成本高）、事后 review（偏离越远修复越贵）、prompt 约束（无持久化，每次重复）。

## 3. 核心假设

<!-- 做了之后会怎样。回答"在验证什么假设"
  - 假设 = 1 句因果句（"做了 X → 用户会 Y"），验证方式 = 可执行的检查
  - EXCLUDE: 多个假设混在一起、技术方案、实现细节 -->

**在 agent 执行过程中施加分阶段约束 → agent 输出质量显著高于自由发挥，且总时间不比事后修复更长。**

验证方式：端到端执行不报错，输出符合预期。作者本人在实际项目中持续使用。

## 4. 方案

<!-- 做什么（不是怎么做）。回答"用户体验怎么变"
  - 用 before → after 格式描述用户行为变化，每个变化点 1 句
  - 任务拆分: 链接到每个 tech 文档（树状向下索引，不回指 roadmap）
  - EXCLUDE: 操作流程图、交互细节、内部数据结构、存储格式、算法、文件路径 -->

- **Before**: 用户写完 prompt 后 agent 自由发挥，事后发现偏离 → **After**: `/sprint` 一条命令启动，AI 自动裁剪阶段、分步执行、关键点暂停确认
- **Before**: 大任务一口气做完，中间无法检查 → **After**: 自动拆分为多个子任务，每个任务独立验证
- **Before**: 简单任务也走完整流程 → **After**: 复杂度自动裁剪，跳过不必要的阶段

## 5. 验收标准

<!-- 怎么算做完了。回答"验收标准"
  - 条目列表，每条格式 = "用户做 X → 应看到 Y"，覆盖核心场景+关键边界，每条可独立验证
  - EXCLUDE: 单元测试用例、代码覆盖率、内部接口断言 -->

- 用户调用 `/sprint {description}` → AI 评估复杂度并生成裁剪后的流水线
- 简单任务描述 → 自动跳过 brainstorm/design/review，只走必要阶段
- 每个阶段产出 handoff 文档 → 下游阶段正确读取并使用
- 关键决策点 → AI 暂停等待用户确认
- `/todo` 快速入口 → 小任务直接执行，不走完整流程
- `/long-sprint` → 大任务拆为多个子 sprint 顺序执行
