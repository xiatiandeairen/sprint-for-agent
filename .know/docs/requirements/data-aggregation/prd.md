## 1. 问题

<!-- 为什么要做这个需求。回答"值不值得做"
  - 3 要素，每要素 1-2 句: 用户痛点（具体困难）、影响范围（多少人/多频繁）、为什么现在做（触发事件）
  - EXCLUDE: 技术实现原因、内部架构限制 -->

sprint 每次执行结束只能看到当次统计（耗时、anchor 结果），无法看到跨 sprint 的整体趋势和价值产出。用户和内部工具都缺少"sprint 用得怎么样"的全局视角。v1 完成后 sprint 已在多项目持续使用，积累了足够数据，是建立可观测性的时机。

## 2. 目标用户

<!-- 给谁做。回答"谁会用"
  - 用户角色 + 使用场景 + 当前替代方案及其不足
  - EXCLUDE: 系统内部组件名、数据模型 -->

两类消费者：内部工具（优化 sprint 流程自身）和使用 sprint 的开发者（优化工作习惯）。当前替代方案是手动翻 `.sprint/` 目录下的 metrics.log 和 handoff 文件，逐个计算统计，不可规模化。

## 3. 核心假设

<!-- 做了之后会怎样。回答"在验证什么假设"
  - 假设 = 1 句因果句（"做了 X → 用户会 Y"），验证方式 = 可执行的检查
  - EXCLUDE: 多个假设混在一起、技术方案、实现细节 -->

**提供跨 sprint 聚合查询命令 → 用户能一条命令看到效率/质量/价值趋势，为流程优化和工作改进提供数据依据。**

验证方式：`sprint-ctl stats` 输出三类聚合指标；`--last N` 和 `--status` 过滤正常工作。

## 4. 方案

<!-- 做什么（不是怎么做）。回答"用户体验怎么变"
  - 用 before → after 格式描述用户行为变化，每个变化点 1 句
  - 任务拆分: 链接到每个 tech 文档（树状向下索引，不回指 roadmap）
  - EXCLUDE: 操作流程图、交互细节、内部数据结构、存储格式、算法、文件路径 -->

- **Before**: sprint 结束后只看到当次耗时和 anchor 结果 → **After**: `sprint-ctl stats` 输出跨 sprint 聚合趋势
- **Before**: 想知道"最近 sprint 是变快了还是变慢了"需要手动翻文件 → **After**: `sprint-ctl stats --last 10` 一条命令

### 聚合指标

| 类别 | 指标 |
|------|------|
| 效率 | 总 sprint 数、完成率、平均耗时、阶段耗时分布 |
| 质量 | anchor 通过率、scope creep 率 |
| 价值 | 任务完成率、偏差分类分布、rework 率 |

### 过滤能力

- `--last N` — 只看最近 N 次 sprint
- `--status completed` — 只看已完成的 sprint

## 5. 验收标准

<!-- 怎么算做完了。回答"验收标准"
  - 条目列表，每条格式 = "用户做 X → 应看到 Y"，覆盖核心场景+关键边界，每条可独立验证
  - EXCLUDE: 单元测试用例、代码覆盖率、内部接口断言 -->

- `sprint-ctl stats` → 输出当前项目所有 sprint 的效率/质量/价值三类指标
- `sprint-ctl stats --last 5` → 只聚合最近 5 次 sprint
- `sprint-ctl stats --status completed` → 只聚合已完成的 sprint
- 无 sprint 数据时 → 输出"No sprints found."
- 只有 1 次 sprint 时 → 输出该次数据，不报错
- 价值指标（任务完成率、偏差分布、rework 率）从 handoff 文件解析 → 缺少 handoff 时标注 N/A
- 回归测试通过
