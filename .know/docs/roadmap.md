# sprint-for-agent 产品路线图



## 1. 产品愿景

### 产品核心

- **定位**: 面向 AI 编程代理的结构化任务执行引擎
- **动机**: AI agent 执行复杂任务时方向偏离、过程不可见、质量不可控，现有方案（人工监督或 prompt 约束）不可规模化且无持久性
- **长远愿景**: AI agent 在任何项目中都像有纪律的工程师一样工作：评估复杂度、分阶段执行、在关键节点自我校验、事后反思改进

### 价值体系


| 层级       | 价值                                             | 衡量指标                                                                 |
| -------- | ---------------------------------------------- | -------------------------------------------------------------------- |
| **即时价值** | agent 每次执行都有结构化约束，方向偏离在阶段边界被拦截                 | anchor 通过率（实测: 46 个测试全通过）、阶段 gate 确认次数（无数据，尚无采集手段）                   |
| **累积价值** | 执行数据持续积累，效率和质量趋势可追溯，流程优化有数据依据                  | 跨 sprint 统计可用性（实测: stats 命令可聚合）、insight 历史对比可用性（实测: ≥2 sprint 后自动展示） |
| **战略价值** | AI 协作从"自由发挥后修复"升级为"约束下执行"，agent 可靠性从依赖运气变为依赖流程 | 无数据（尚无跨项目可靠性对比手段）                                                    |


### 核心问题


| 问题                     | 发生频率                          | 单次成本                                 | 影响面                     | 现有应对                   |
| ---------------------- | ----------------------------- | ------------------------------------ | ----------------------- | ---------------------- |
| AI agent 执行复杂任务时方向偏离   | 每次复杂任务（估算: 日均 2-5 次，基于作者使用频率） | 估算 10-30 分钟返工 + 引入回归风险（基于作者体感，未精确计时） | 所有使用 AI agent 做工程任务的开发者 | 人工全程盯着（注意力成本高），不可规模化   |
| agent 执行过程不可见，偏离难以及时发现 | 每次超过 3 步的任务（估算: 日均 3-10 次）    | 偏离越深修复成本越高，估算浪费 50% 以上已执行工作量         | 同上                      | 事后 review（偏离已造成，修复成本高） |
| 简单任务走完整流程太重，不走又没保障     | 每次小任务（估算: 日均 5-15 次）          | 完整流程浪费 5-10 分钟，跳过流程则无质量保障            | 同上                      | prompt 约束（无持久化，每次重复写）  |


### 目标用户


| 角色                      | 典型场景                  | Before                              | After                                         | 预估提效                           |
| ----------------------- | --------------------- | ----------------------------------- | --------------------------------------------- | ------------------------------ |
| 使用 Claude Code 的独立开发者   | 用 agent 实现功能、修 bug、重构 | 每次复杂任务需人工监督或事后修复（估算: 单次 10-30 分钟返工） | `/sprint` 一条命令启动，自动裁剪阶段、分步执行、关键点暂停确认          | 待验证（预期: 单次复杂任务节省 10-20 分钟返工时间） |
| 使用 AI agent 维护中大型项目的开发者 | 跨模块大任务拆分执行            | 大任务一口气做完中间无法检查，偏离后全部返工              | `/long-sprint` 自动拆分子 sprint，每个独立交付验证，方向锁定防止漂移 | 待验证（预期: 大任务成功率显著提升）            |


### 竞品对比


| 方案                    | 定位                           | 目标用户           | 核心功能                                    | 优势                                         | 局限                                        |
| --------------------- | ---------------------------- | -------------- | --------------------------------------- | ------------------------------------------ | ----------------------------------------- |
| **sprint-for-agent**  | 面向 AI 编程代理的结构化任务执行引擎         | Claude Code 用户 | 复杂度裁剪、阶段流水线、anchor 验证、模型路由、跨 sprint 可观测 | 执行约束而非辅助，7 种 anchor 类型保障结构不变量，自动适配 7 种语言生态 | 仅支持 Claude Code，学习曲线存在（7 阶段概念），依赖 python3 |

| Cursor Rules          | IDE 级 AI 编程约束配置              | Cursor 用户      | 项目规则、文件级规则、glob 匹配                      | IDE 深度集成，规则可按文件粒度控制                        | 仅限 Cursor，无阶段化执行，无结构验证，无跨任务可观测性           |

### 版本详情

#### v1 — 单项目可用

- **战略意图**: 验证核心假设——在 agent 执行过程中施加分阶段约束是否比自由发挥产出更高质量结果
- **投入产出**: 投入 6 天全职开发 → 建立端到端分阶段执行能力（3 个 skill + 7 个 stage + 3 个脚本）
- **优先级依据**: 核心闭环未验证前后续版本无意义，无外部依赖，可立即启动
- **风险与依赖**: 依赖 Claude Code plugin 机制稳定性；风险：stage 文件过长导致 token 消耗
- **成功指标**: 端到端执行不报错，作者在 ≥2 个不同项目中持续使用
- **核心价值**: 1. 首次可以用 `/sprint` 一条命令驱动结构化任务执行 2. 首次可以用 anchor 验证结构不变量 3. 首次可以用 `/long-sprint` 编排大任务
- **用户覆盖**: 作者 dogfood
- **核心指标**（基线 → v1）:


| 指标       | 基线       | v1                                         | 变化   | 来源                                        |
| -------- | -------- | ------------------------------------------ | ---- | ----------------------------------------- |
| 测试覆盖     | 0 case   | 46 case                                    | ↑ 46 | test-sprint-ctl.sh + test-anchor-check.sh |
| 语言生态支持   | 1（Swift） | 7（Swift, JS, Rust, Make, Python, Go, Ruby） | ↑ 6  | anchor-check.sh detect 函数                 |
| skill 数量 | 0        | 3（sprint, long-sprint, todo）               | ↑ 3  | skills/ 目录                                |
| stage 数量 | 0        | 7（brainstorm→insight）                      | ↑ 7  | stages/ 目录                                |


#### v2 — 可观测

- **战略意图**: v1 验证了执行约束有效，但执行数据只写不读——需要建立数据消费能力让用户和内部工具都能从积累的数据中获益
- **投入产出**: 投入 1 天 → 建立跨 sprint 聚合查询和 insight 历史对比能力
- **优先级依据**: v1 已积累足够数据，是建立可观测性的时机；无前置依赖
- **风险与依赖**: 风险：metrics.log 格式不统一导致聚合解析困难；历史数据不完整导致趋势分析样本不足
- **成功指标**: `sprint-ctl stats` 输出聚合统计，insight 输出包含历史完成率和时间趋势
- **核心价值**: 1. 首次可以用一条命令查看跨 sprint 效率/质量/价值趋势 2. insight 阶段自动展示历史对比
- **用户覆盖**: 作者 dogfood
- **核心指标**（v1 → v2）:


| 指标           | v1  | v2                    | 变化  | 来源                      |
| ------------ | --- | --------------------- | --- | ----------------------- |
| 聚合查询命令       | 0   | 1（stats）              | ↑ 1 | sprint-ctl.sh stats     |
| insight 历史指标 | 0   | 3（耗时、anchor 率、task 率） | ↑ 3 | sprint-insight-stats.sh |
| 过滤维度         | 0   | 2（--last N, --status） | ↑ 2 | sprint-ctl.sh stats     |


#### v3 — 产品成熟

- **战略意图**: v1+v2 功能完整但产品化程度未经系统评估——通过成熟度框架审视并消除规则矛盾、流程缺口、可靠性短板
- **投入产出**: 投入 1 天 → 消除 2 处规则矛盾、补全 2 处流程缺口、增加防御性检查和 6 个测试
- **优先级依据**: 功能层完整后是打磨质量的最佳时机；规则矛盾会导致实现者困惑，越早修复越好
- **风险与依赖**: 无已识别风险和外部依赖
- **成功指标**: 4 维度成熟度评估全部达到 L2+，0 处规则矛盾，52 tests 全通过
- **核心价值**: 1. 规则自洽——实现者不再需要猜测哪个规则优先 2. 流程闭环——doc 模式和 quality handoff 不再有未定义行为 3. 脚本更健壮——缺 python3 或参数为空时有明确错误提示
- **用户覆盖**: 作者 dogfood
- **核心指标**（v2 → v3）:


| 指标     | v2      | v3      | 变化  | 来源                                       |
| ------ | ------- | ------- | --- | ---------------------------------------- |
| 测试覆盖   | 46 case | 52 case | ↑ 6 | test-insight-stats.sh 新增                 |
| 规则矛盾   | 2 处     | 0 处     | ↓ 2 | SKILL.md Rule 8 + Evaluate 段修复           |
| 流程缺口   | 2 处     | 0 处     | ↓ 2 | quality.md handoff + execute.md doc mode |
| 脚本防御检查 | 0 处     | 3 处     | ↑ 3 | python3 检查 ×2 + create 参数校验              |


#### v4 — stage 深度审计 + 衔接清理

- **战略意图**: v3 执行框架稳定后，通过 ONE JOB 审计 + 马斯克对抗性审视，清理 stage 职责重叠、消除决策重复、优化审查深度、前置需求合法性闸门。sprint 从"能跑"升级为"每个 stage 职责纯净且衔接高效"
- **投入产出**: 5 项里程碑全部完成 → stage 职责清晰化、决策衔接去重、review 深度自适应、需求伪需求早拦截
- **优先级依据**: 来源于 2026-04-17 的 ONE JOB 深度审计。方法论匹配（原 M11）和检查点回顾（原 M12）需要 evolution v0.2 的验证数据背书，且误报率未知，移出本版本范围，待真需求被数据证明后再规划
- **风险与依赖**: 无已识别风险和外部依赖
- **成功指标**: 5 项 stage 职责改进全部落地，review 深度档位新增 quick 分级，plan-design Q1-Q4 重复率降为 0，Sanity Gate 至少拦截 1 次伪需求
- **核心价值**: 1. review 深度分级（quick/full）+ L4 signal 按改动类型过滤 2. plan-design 决策衔接（消除 Q1-Q4 重复提问）3. stage 职责收敛（Value Mining 归位、uncommitted 移出 insight）4. design 建议任务边界 5. brainstorm Sanity Gate 破 AI 顺从病（需求合法性闸门，非分析能力）
- **用户覆盖**: 作者 dogfood
- **核心指标**（v3 → v4）:

| 指标 | v3 | v4 | 变化 | 来源 |
|------|------|------|------|------|
| review 深度档位 | 1（full） | 2（quick/full） | ↑ 1 | review-optimization PRD |
| stage 职责纯度 | 4/6 stage 有偏离 Step | 6/6 stage 无偏离 | — | ONE JOB 审计 |
| plan Q1-Q4 重复率 | 每次 design+plan 都问 | design 存在时跳过 | ↓ | plan-design-handoff PRD |
| design 任务边界提示 | 无 | 有 Suggested Task Boundaries | ↑ | design-task-boundary-hints PRD |
| brainstorm 需求闸门 | 无 | Sanity Gate 5 问过滤 | ↑ | 2026-04-17 sprint |
