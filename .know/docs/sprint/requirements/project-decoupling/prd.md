## 1. 问题

<!-- 为什么要做这个需求。回答"值不值得做"
  - 3 要素，每要素 1-2 句: 用户痛点（具体困难）、影响范围（多少人/多频繁）、为什么现在做（触发事件）
  - EXCLUDE: 技术实现原因、内部架构限制 -->

sprint 的构建和导入验证只能在特定 Swift 项目上运行，非 Swift 项目使用时验证直接失败。所有想在非 Swift 项目上使用 sprint 的开发者都受影响。M1 完成后流水线可用，消除语言耦合是让产品真正通用化的前提。

## 2. 目标用户

<!-- 给谁做。回答"谁会用"
  - 用户角色 + 使用场景 + 当前替代方案及其不足
  - EXCLUDE: 系统内部组件名、数据模型 -->

使用 sprint 驱动任务执行的开发者，项目语言不限于 Swift。典型场景：在 TypeScript/Go/Rust 等项目上使用 sprint 时构建验证失败。当前替代方案是跳过构建类 anchor（丧失核心验证能力）或手改脚本（不可维护）。

## 3. 核心假设

<!-- 做了之后会怎样。回答"在验证什么假设"
  - 假设 = 1 句因果句（"做了 X → 用户会 Y"），验证方式 = 可执行的检查
  - EXCLUDE: 多个假设混在一起、技术方案、实现细节 -->

**将构建/测试/导入验证从硬编码改为动态检测 → 用户在任意语言项目上都能使用完整的 anchor 验证，不需要改 sprint 源码。**

验证方式：在非 Swift 项目上执行包含 MUST_BUILD、MUST_TEST、MUST_IMPORT 的 sprint，端到端通过。

## 4. 方案

<!-- 做什么（不是怎么做）。回答"用户体验怎么变"
  - 用 before → after 格式描述用户行为变化，每个变化点 1 句
  - 任务拆分: 链接到每个 tech 文档（树状向下索引，不回指 roadmap）
  - EXCLUDE: 操作流程图、交互细节、内部数据结构、存储格式、算法、文件路径 -->

- **Before**: 非 Swift 项目上 MUST_BUILD 直接失败 → **After**: 自动检测项目类型并使用对应命令
- **Before**: 接入新项目需要手改脚本 → **After**: 零配置，自动检测 7 种语言

## 5. 验收标准

<!-- 怎么算做完了。回答"验收标准"
  - 条目列表，每条格式 = "用户做 X → 应看到 Y"，覆盖核心场景+关键边界，每条可独立验证
  - EXCLUDE: 单元测试用例、代码覆盖率、内部接口断言 -->

- 在 package.json 项目上使用 MUST_BUILD → 执行 `npm run build` 并正确判断成功/失败
- 在 Cargo.toml 项目上使用 MUST_TEST → 执行 `cargo test` 并正确判断成功/失败
- MUST_IMPORT 使用相对路径搜索，按语言选择导入语法
- 未检测到项目类型 → MUST_BUILD/MUST_TEST 报 SKIP（不是 FAIL）
- 现有 MUST_EXIST/MUST_NOT_EXIST/FILE_NOT_MODIFIED 行为不变
