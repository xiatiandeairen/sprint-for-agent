## 1. 问题

<!-- 为什么要做这个需求。回答"值不值得做"
  - 3 要素，每要素 1-2 句: 用户痛点（具体困难）、影响范围（多少人/多频繁）、为什么现在做（触发事件）
  - EXCLUDE: 技术实现原因、内部架构限制 -->

sprint 的构建/测试命令配置混在 AI 指令文件中，用户不知道该在哪里配置项目信息。且当前只支持 build 和 test，无法配置 lint 命令。随着 sprint 在更多项目上使用（M2 已消除语言耦合），需要一个专用的配置入口。

## 2. 目标用户

<!-- 给谁做。回答"谁会用"
  - 用户角色 + 使用场景 + 当前替代方案及其不足
  - EXCLUDE: 系统内部组件名、数据模型 -->

使用 sprint 驱动任务执行的开发者，需要为项目指定构建/测试/lint 命令。当前替代方案是在 CLAUDE.md 中写配置，但这不是正式的配置机制，没有文档说明，不支持 lint。

## 3. 核心假设

<!-- 做了之后会怎样。回答"在验证什么假设"
  - 假设 = 1 句因果句（"做了 X → 用户会 Y"），验证方式 = 可执行的检查
  - EXCLUDE: 多个假设混在一起、技术方案、实现细节 -->

**提供独立的项目级配置文件 → 用户接入新项目只需写 1 个配置文件，不需要了解 sprint 内部逻辑。**

验证方式：在新项目中创建配置文件，sprint 的 anchor-check 和 quality 阶段正确使用配置的命令。

## 4. 方案

<!-- 做什么（不是怎么做）。回答"用户体验怎么变"
  - 用 before → after 格式描述用户行为变化，每个变化点 1 句
  - 任务拆分: 链接到每个 tech 文档（树状向下索引，不回指 roadmap）
  - EXCLUDE: 操作流程图、交互细节、内部数据结构、存储格式、算法、文件路径 -->

- **Before**: 在 CLAUDE.md 写构建配置（不直观，不支持 lint） → **After**: 创建 `.sprint.json`，声明 build/test/lint 命令，sprint 自动读取
- **Before**: 不知道该在哪里配置 → **After**: 一个专用配置文件，格式简单明确

## 5. 验收标准

<!-- 怎么算做完了。回答"验收标准"
  - 条目列表，每条格式 = "用户做 X → 应看到 Y"，覆盖核心场景+关键边界，每条可独立验证
  - EXCLUDE: 单元测试用例、代码覆盖率、内部接口断言 -->

- 有 `.sprint.json` 且包含 build 字段 → MUST_BUILD 使用配置命令
- 有 `.sprint.json` 且包含 lint 字段 → quality 阶段执行 lint
- `.sprint.json` 缺少字段 → 回退到已有检测机制
- 无 `.sprint.json` → 行为与之前完全一致
- `.sprint.json` 格式错误 → 报明确错误信息
