# clarify

## Purpose

把模糊需求对齐成可传递给下一阶段的目标契约。

只回答一件事：**要解决什么，边界是什么，怎样算解决了**。

不做：
- 不做方案设计
- 不做价值挖掘
- 不拆任务
- 不记录完整对话过程

## Steps

### 1. 判断是否需要澄清

目标：决定是直接锁定目标，还是进入结构化澄清。

步骤：

1. 理解用户输入 desc。
2. 检查 4 个最小闭环字段：
  - **Goal**：要达成什么
  - **Object**：作用对象是什么
  - **Scope**：本期包含 / 不包含什么
  - **Success**：怎样算完成正确
3. 判定：
  - 4 个字段都清楚，且不存在高风险误解 → 跳到 §5，让用户决定是否审视
  - 4 个字段都清楚，但存在高风险误解 → 进入 §4
  - 任一字段缺失 → 进入 §2

不向用户展示内部判定过程。

### 2. 识别模糊点

目标：聚焦真正会影响后续方向的模糊维度，不让用户从完整方案里单选。

步骤：

1. 从用户输入中找出 1-4 个模糊点。
2. 每个模糊点必须满足至少一个条件：
  - 会改变目标
  - 会改变作用对象
  - 会改变范围
  - 会改变成功标准
  - 会导致后续 design / plan 做错方向
3. 为每个模糊点给 2-5 个结构化猜测方向。
4. 选项允许多选，用户也可以直接改写。

展示模板；输出后暂停，等待用户回复：

```markdown
这些点如果理解错，后面容易做偏。每项可多选，也可以直接改写：

1. 你说的「{原词或问题}」主要指：
  - A. {猜测方向}
  - B. {猜测方向}
  - C. {猜测方向}

2. 你最想得到的是：
  - A. {猜测方向}
  - B. {猜测方向}
  - C. {猜测方向}

回复示例：1 选 A/C，2 全选，另外补充...
```

规则：

- 不生成 A/B/C 三个完整候选方案。
- 不为了凑数量制造明显错误的陪跑项。
- 每个选项必须是用户可能组合使用的维度选择。
- 如果只有 1 个明确模糊点，只问 1 个。

### 3. 生成动态目标草案

目标：把用户选择收敛成目标草案，并只展示当前场景需要确认的字段。

核心字段：

| 字段 | 说明 |
|---|---|
| Goal | 要达成什么 |
| Object | 作用对象 |
| Scope | 本期包含 / 不包含什么 |
| Success | 怎样算完成正确 |

按需字段：

| 字段 | 触发条件 |
|---|---|
| Actor | 涉及用户、角色、权限、协作流程 |
| Context | 背景会影响目标判断，或用户主动提到原因 |
| Constraint | 涉及时间、兼容性、技术边界、不能做什么 |
| Priority | 多个目标互相冲突 |
| Risk | 存在高代价误解 |

步骤：

1. 基于用户输入和 §2 的回复生成目标草案。
2. 只展示核心字段和被触发的按需字段。
3. 字段缺失但不阻塞下一阶段时，写 `未指定，不阻塞`，不要追问。
4. 字段缺失且会导致方向偏差时，列入“还需要确认”。

展示模板；输出后暂停，等待用户回复：

```markdown
基于你的选择，我当前理解是：

- 要解决的问题：{问题}
- 要改/要产出的对象：{作用对象}
- 这次会做：
  - {包含}
- 这次不做：
  - {不包含}
- 怎样算做好：{成功标准}
- {按需补充的问题式标题}: {内容}

还需要确认：
1. {只问会影响方向的问题}
2. {只问会影响方向的问题}
```

用户修正后，更新草案。最多做 1 轮跟进；仍有非阻塞缺口时写入 `遗留问题 / 风险`。

### 4. 风险化假设确认

目标：只确认会导致后续跑偏的高风险假设。

进入条件：

- 存在模型推断出来、但用户没有直接确认的承重前提
- 该前提一旦错误，会改变目标 / 范围 / 成功标准

步骤：

1. 列出最多 3 条高风险假设。
2. 每条都写清楚“如果错了会怎样”。
3. 用户可回答：对 / 错 / 部分对。
4. 没有高风险假设时跳过本步骤。

展示模板：

```markdown
下面这些如果理解错，会导致后续跑偏：

| 我现在的理解 | 理解错会导致 | 请回复 |
|---|---|---|
| {具体理解} | {具体后果} | 对 / 不对 / 一半对 |
```

规则：

- 不凑满 3 条。
- 不写无法反驳的废话。
- 不记录被用户否掉的假设到最终结果；只记录确认后仍影响后续的内容。

### 5. 可选审视

目标：在目标锁定前，让用户决定是否需要反向检查。

步骤：

1. 基于当前目标草案，询问用户是否审视；输出后暂停，等待用户回复。
2. 用户选择不审视 → 进入 §6。
3. 用户选择审视 → 切换为挑战者角色，只质疑目标契约本身。
4. 审视后给出结论：
  - 目标不变：说明“审视后不调整”，进入 §6
  - 目标需调整：列出建议调整点；输出后暂停，等待用户回复；确认后进入 §6

展示模板：

```markdown
目标已基本对齐。要不要做一次反向检查？

- 跳过检查：直接锁定目标
- 做检查：我会从“问题是不是真的、这次做的是不是太多、怎样算做好是否清楚”三个角度挑问题
```

审视规则：

- 只审视 clarify 结果，不进入方案设计。
- 只挑战要解决的问题、这次会做 / 不做什么、怎样算做好、关键决定。
- 不新增价值挖掘。
- 不把审视过程写入 handoff；只写被用户确认的调整结果。

### 6. 进入锁定前检查

目标：确认目标契约已经足够进入最终锁定，并处理用户在最后确认前的改动。

步骤：

1. 检查要解决的问题、作用对象、本期范围、做好标准是否都足够支撑下一阶段。
2. 根据检查结果处理：
  - 都已足够 → 进入 §7
  - 仍缺任一阻塞字段 → 停止，明确说缺哪一项；输出后暂停，等待用户回复
  - 用户拒绝当前草案 → 回到 §2，重新识别模糊点；不要继续堆问题
  - 用户给出新目标 → 把新目标作为 desc 重新跑 §1
  - 用户说“先这样” → 把未确认但不阻塞的内容写入 `遗留问题 / 风险`，进入 §7

### 7. 锁定目标

目标：给用户展示最终目标契约，并写入 handoff。

步骤：

1. 确认以下条件都成立：
  - 要解决的问题、作用对象、本期范围、做好标准都已足够支撑下一阶段
  - 阻塞性问题已被用户确认或修正
  - 高风险假设已确认，或不存在高风险假设
  - 用户已决定是否做反向检查；如已检查，调整结果已确认
2. 给用户展示最终目标摘要。
3. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。

展示模板：

```markdown
已对齐目标 ✓

要解决的问题：{一句话}
这次会做：{包含摘要}
这次不做：{不包含摘要}
怎样算做好：{成功标准摘要}
```

handoff 模板：

```markdown
已对齐需求:
{一句话说明已确认目标}

范围约定:
- 做: {本期明确包含}
- 不做: {本期明确不做}
- 做好标准: {可验证完成标准}

已确认决定:
- {用户确认过、会影响后续阶段的决定；没有写 None}

遗留问题 / 风险:
- {未确认但不阻塞，或需要后续阶段注意的风险；没有写 None}
```

规则：

- 不记录候选项。
- 不记录中间问答。
- 不记录被否掉的猜测。
- 不记录内部模糊点判定。
- `已确认决定` 只写用户确认过的结果。
- `遗留问题 / 风险` 只写不阻塞但会影响下游判断的内容。
- 只有完成本步骤的展示和 handoff 写入，clarify 才算完成。
