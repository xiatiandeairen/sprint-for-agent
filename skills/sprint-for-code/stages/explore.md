# explore

## Purpose

在需求已经明确的前提下，判断是否值得向上挖一层，发现更高层级的隐形需求。

只回答一件事：**这次需求是一次性修补，还是某个可复用机制的信号**。

不做：
- 不重新澄清需求
- 不做方案设计
- 不拆任务
- 不自动扩大本期范围
- 不递归深挖

## Steps

### 1. 判断是否值得探索

目标：先判断当前需求有没有向上挖的价值。

步骤：

1. 读取 clarify 产出的目标契约；如果没有 clarify，就使用用户原始描述。
2. 检查以下信号：
  - 是否像反复出现的问题
  - 是否只是某个流程里的局部症状
  - 是否暴露了隐含规则、隐含判断或隐含协作成本
  - 是否可能通过模板化、自动化、机制化放大收益
  - 如果只做当前需求，是否很快会出现相邻需求
3. 判定：
  - 没有明显信号 → 进入 §5，直接记录“未发现值得深挖的上层需求”
  - 有 1-4 个信号 → 进入 §2

不向用户展示内部判断表。

### 2. 展示可深挖方向

目标：让用户决定是否深挖、深挖哪些方向。

步骤：

1. 把命中的信号转成 1-4 个用户能理解的方向。
2. 每个方向说明：
  - 看到的迹象
  - 可能对应的上层问题
  - 深挖后可能得到什么
3. 用户可以多选，也可以跳过。

展示模板；输出后暂停，等待用户回复：

```markdown
当前需求已经明确，但我看到几个可能值得向上挖的方向。你可以选一个、多个，或跳过：

1. {方向名}
   我看到的迹象：{来自需求的具体迹象}
   可能不只是：{当前需求}
   可能是在处理：{更高层级问题}
   深挖后可能得到：{规则 / 模板 / 自动化 / 流程调整 / 后续机会}

2. {方向名}
   我看到的迹象：...
   可能不只是：...
   可能是在处理：...
   深挖后可能得到：...

回复示例：选 1/3，或“跳过”。
```

规则：

- 不超过 4 个方向。
- 不给明显陪跑项。
- 不把方向写成解决方案。
- 方向必须来自当前需求证据，不能凭空联想。
- 用户跳过 → 进入 §5。

### 3. 深挖选中的方向

目标：对用户选中的方向各深挖一层，产出可决策的上层需求候选。

步骤：

1. 对每个选中方向生成一条上层需求候选。
2. 每条候选必须说明：
  - 当前需求是什么
  - 背后可能的问题是什么
  - 如果只做当前需求，会漏掉什么
  - 如果向上处理，可能得到什么
  - 会不会扩大本期范围
3. 让用户决定每条候选怎么处理；输出后暂停，等待用户回复。

展示模板：

```markdown
针对你选的方向，我建议这样看：

1. {方向名}
   当前要做的是：{当前需求}
   背后可能的问题是：{上层问题}
   如果只做当前需求：{可能遗漏}
   如果向上处理：{可能收益}
   对本期范围的影响：{不扩大 / 小幅扩大 / 明显扩大}

   请选择：
   - A. 加入本期
   - B. 记录后续
   - C. 不采纳
```

规则：

- 每个方向只深挖一层。
- 默认不建议加入本期，除非低成本且强相关。
- 明显扩大范围的候选只能建议“记录后续”。
- 用户可以改写候选内容。

### 4. 范围保护

目标：防止 explore 把明确需求膨胀成大任务。

步骤：

1. 汇总用户在 §3 的选择。
2. 如果有“加入本期”的项，检查是否满足：
  - 与原目标强相关
  - 不改变主要作用对象
  - 不需要新的设计方向
  - 不显著增加实现规模
3. 判定：
  - 全部满足 → 允许进入本期补充
  - 任一不满足 → 改为“后续机会”，并告诉用户原因
4. 如果用户坚持加入，要求用户确认这是范围变更；输出后暂停，等待用户回复。

展示模板；输出后暂停，等待用户回复：

```markdown
这些内容会影响本期范围，我先做一次范围检查：

| 项目 | 判断 | 原因 |
|---|---|---|
| {候选} | 可加入本期 / 建议放后续 | {原因} |

需要你确认：
- 可加入本期的项会写入本期补充
- 建议放后续的项会写入后续机会
```

进入 §5 前检查：

- 用户已选择深挖方向，或明确跳过
- 被深挖的方向都有处理结论：加入本期 / 记录后续 / 不采纳
- 加入本期的内容已通过范围保护；未通过但用户坚持加入的，已被用户确认为范围变更

### 5. 锁定探索结果

目标：给用户展示最终探索结论，并写入 handoff。

步骤：

1. 确认以下条件都成立：
  - 用户已选择深挖方向，或明确跳过
  - 被深挖的方向已有处理结论：加入本期 / 记录后续 / 不采纳
  - 加入本期的内容已通过范围保护；未通过但用户坚持加入的，已被用户确认为范围变更
2. 给用户展示探索结果。
3. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。

展示模板：

```markdown
探索结果已确认 ✓

本期补充：
- {低成本且强相关的补充；没有写“无”}

后续机会：
- {有价值但不进本期的上层需求；没有写“无”}

不采纳：
- {用户明确不采纳的方向；没有写“无”}
```

handoff 模板：

```markdown
- 结论: {一句话说明是否发现值得处理的上层需求}
- 本期补充: {加入本期的内容；多项用 `；` 分隔；没有则省略本行}
- 后续机会: {记录后续的内容；多项用 `；` 分隔；没有则省略本行}
- 不采纳: {用户明确不采纳的内容；多项用 `；` 分隔；没有则省略本行}
```

规则：

- 不记录内部信号判断。
- 不记录完整问答。
- 不记录被模型提出但用户没选的方向，除非用户要求保留。
- `本期补充` 必须能被后续 design / plan 消费。
- `后续机会` 只记录价值，不改变本期目标。
- `不采纳` 只记录用户明确否掉的方向。
- handoff 里不要输出空标题；没有内容的字段直接省略，不写 None / 无。
- 只有完成本步骤的展示和 handoff 写入，explore 才算完成。
