# plan

## Purpose

把可用上下文转成可执行、可验证、可判断并行性的任务计划。

只回答一件事：**后续执行者要按什么任务、什么规格、什么顺序执行，并怎样验收**。

不做：
- 不重新定义需求
- 不继续挖隐形需求
- 不重新设计接口 / 流程 / 数据
- 不写代码
- 不静默扩大范围

## Steps

### 1. 读取可用上下文

目标：明确 plan 可以使用哪些已确认内容，哪些不能重新讨论。

步骤：

1. 读取可用上下文。可用上下文可能包括：
  - 用户原始描述
  - 已确认目标 / 范围 / 成功标准
  - 已确认设计契约
  - 已确认执行约束
  - 已有风险 / 约束
  - 已有代码定位结果
2. 提取：
  - 设计契约
  - `后续不应重新讨论`
  - 设计约束
  - 需求支撑检查
  - 待定 / 风险
3. 如果没有已确认设计契约，则基于当前上下文生成最小可执行计划；只补足任务拆分所需输入，不补做完整 design。
4. 判断是否存在设计缺口：
  - 如果缺口会影响接口、数据、流程、兼容、错误处理 → 停止并输出阻塞项：缺少什么、为什么阻塞、需要补充什么
  - 如果缺口只影响执行方式 → 进入 §2

展示模板：

```markdown
我会基于这些已确认内容拆计划：

- 目标：{目标}
- 设计方向：{设计方向}
- 不重新讨论：
  - {已确认设计决定}
- 需要注意：
  - {待定 / 风险}
```

### 2. 确认执行规格

目标：确认后续执行者按什么执行标准工作。

规格维度：

- 改动范围：只改必要部分 / 顺手清理
- 处理深度：先堵住 / 追根因
- 过渡方式：直接替换 / 分阶段迁移
- 兼容要求：保持调用方不变 / 允许内部破坏性调整
- 测试标准：最小验证 / 覆盖相邻风险
- 依赖策略：不新增依赖 / 允许引入成熟库
- 质量线：是否允许临时兼容层、重复代码、TODO
- 执行节奏：顺序 / 并行 / 循环

步骤：

1. 从可用上下文继承已明确规格。
2. 从风险和任务规模推断建议规格。
3. 只展示会影响任务切分或执行行为的规格。
4. 用户确认或修改。
5. 如果用户修改导致设计决定变化 → 停止并输出设计决定缺口。

展示模板：

```markdown
进入任务拆分前，需要确认执行规格：

| 规格 | 当前建议 | 为什么 | 请确认 |
|---|---|---|---|
| 改动范围 | 只改必要部分 | 避免范围扩大 | 对 / 改成顺手清理 |
| 处理深度 | 追根因 | 这是反复出现的问题 | 对 / 改成先堵住 |
| 兼容要求 | 保持调用方不变 | 当前上下文未授权破坏性变更 | 对 / 允许内部调整 |
| 测试标准 | 新增逻辑 + 相邻风险点 | 涉及共享模块 | 对 / 降低测试 |
```

规则：

- 不全量询问，只问有影响的规格。
- 能继承的不重复问。
- 规格不能覆盖已确认设计决定。
- 已确认规格写入 handoff。

### 3. 判断是否需要读代码

目标：为文件清单、任务边界和验证命令补足事实。

需要读代码的情况：

- 可用上下文未给出具体文件
- 需要确认测试入口
- 需要确认已有模块位置
- 需要判断任务能否独立拆分
- 需要判断是否能并行
- 需要确认 do-not-touch 文件

不需要读代码的情况：

- 可用上下文已给出明确文件清单
- 单文件改动且路径明确
- 用户只需要粗计划

读代码方式：

1. 只围绕 plan 问题读：
  - 文件在哪里
  - 哪些文件要改 / 不能改
  - 测试命令是什么
  - 任务之间是否有文件冲突
  - 有没有现有测试可复用
2. 不读代码来重新设计。
3. 不改代码。

用户展示模板：

```markdown
我需要看少量代码来补计划事实：

- 定位文件：{模块 / 路径}
- 找验证入口：{测试 / 构建}
- 判断任务边界：{相关区域}

目的：生成可靠的文件清单和验证方式。
```

### 4. 生成文件 / 区域清单

目标：建立任务拆分的边界。

步骤：

1. 生成清单：
  - create
  - modify
  - do-not-touch
  - verify-only
2. 每个文件 / 区域必须有来源：
  - design
  - 代码定位
  - 测试入口
  - 用户指定
3. 后续任务只能引用这个清单里的文件 / 区域。
4. 如果发现文件边界缺失且会影响方案，停止并输出设计边界缺口。

展示模板：

```markdown
文件 / 区域清单：

| 类型 | 路径 / 区域 | 来源 | 用途 |
|---|---|---|---|
| create | ... | 已确认设计 | 新增 ... |
| modify | ... | 代码定位 | 修改 ... |
| do-not-touch | ... | 已确认约束 | 保持兼容 |
| verify-only | ... | 测试入口 | 跑验证 |
```

### 5. 生成验证锚点

目标：把需求、设计约束和执行规格转成后续执行必须满足的检查项。

步骤：

1. 从以下来源提取锚点：
  - 已确认成功标准
  - 已确认本期补充
  - 需求支撑检查
  - 设计契约
  - 执行规格
  - 文件 / 区域清单
2. 每个锚点必须有验证方式：
  - 测试
  - build
  - lint / typecheck
  - 文件存在
  - 内容检查
  - 手动验证
3. 没有验证方式的锚点不能进入计划；要么补验证方式，要么标记为人工验收。

展示模板：

```markdown
验证锚点：

| 必须满足 | 验证方式 | 来源 |
|---|---|---|
| {锚点} | {测试 / build / 内容检查 / 人工验收} | 需求 / 设计 / 规格 |
```

规则：

- 每个任务至少关联一个锚点。
- 每个成功标准至少有一个锚点。
- 锚点不能和已确认设计冲突。

### 6. 任务拆分

目标：把文件清单和锚点转成后续执行者可执行任务。

步骤：

1. 按单一职责拆任务。
2. 每个任务必须包含：
  - 任务名
  - 要改的文件 / 区域
  - 做什么
  - 不做什么
  - 依赖
  - 完成条件
  - AI verify
3. 不混合“新功能”和“重构”。
4. 不把同一共享文件拆到多个并行任务里。
5. 任务太大时继续拆。

展示模板：

```markdown
任务拆分：

| # | 任务 | 文件 / 区域 | 依赖 | 完成条件 | AI verify |
|---|---|---|---|---|---|
| 1 | {任务名} | {文件} | 无 | {完成条件} | {命令 / 检查} |
| 2 | {任务名} | {文件} | Task 1 | {完成条件} | {命令 / 检查} |
```

规则：

- 每个任务必须能独立说明“做完了”。
- 每个任务必须有非空 AI verify。
- AI verify 优先级：测试 > build / typecheck > lint > 文件 / 内容检查 > 人工验收。
- 文件 / 区域必须来自 §4 清单。
- 完成条件必须映射到 §5 锚点。

### 7. 判断执行方式

目标：决定后续执行阶段顺序、并行或循环。

步骤：

1. 根据任务依赖、文件冲突、验证成本判断：
  - sequence：默认
  - parallel：任务互不依赖，文件不冲突，验证可独立
  - loop：需要边做边验证、多轮收敛
2. 给出建议执行方式。
3. 如果用户调整，记录原因。

展示模板：

```markdown
执行方式建议：

- 建议：{sequence / parallel / loop}
- 原因：{依赖 / 文件冲突 / 验证方式}
- 顺序：
  1. {Task}
  2. {Task}
```

parallel 额外输出：

```markdown
可并行：
- {Task A} 与 {Task B}：文件不冲突，验证独立

不可并行：
- {Task C} 与 {Task D}：共享 {file} 或依赖 {reason}
```

### 8. 计划覆盖检查

目标：证明 plan 覆盖了已确认设计契约和需求验证点。

步骤：

1. 检查每个来源是否已被任务或锚点覆盖：
  - 设计改动对象
  - 设计边界
  - 设计验证
  - 需求支撑检查
  - 本期补充
  - 执行规格
2. 未覆盖不能进入 §9。
3. 如果无法覆盖：
  - 停止并输出设计缺口
  - 调整执行规格
  - 降低范围
  - 记录非阻塞风险

展示模板：

```markdown
计划覆盖检查：

| 来源项 | 覆盖方式 | 结论 |
|---|---|---|
| {设计点 / 成功标准} | Task {n} / 锚点 {x} | 已覆盖 / 未覆盖 |
```

### 9. 锁定计划

目标：给用户展示最终计划，并写入 handoff。

步骤：

1. 确认以下条件都成立：
  - 没有阻塞性设计缺口
  - 执行规格已确认
  - 文件 / 区域清单已确认
  - 每个成功标准至少有一个验证锚点
  - 每个任务都有文件范围、依赖、完成条件、AI verify
  - 任务之间依赖和执行方式已明确
  - 计划覆盖检查全部通过
2. 给用户展示最终计划。
3. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。

展示模板：

```markdown
计划已确认 ✓

执行规格：
- {规格摘要}

任务：
1. {任务名} — {完成条件}
2. {任务名} — {完成条件}

执行方式：
{sequence / parallel / loop}

验证：
- {关键验证项}
```

handoff 模板：

```markdown
计划结论:
{一句话}

执行规格:
- 改动范围: ...
- 处理深度: ...
- 过渡方式: ...
- 兼容要求: ...
- 测试标准: ...
- 依赖策略: ...
- 质量线: ...
- 执行节奏: ...

文件清单:
- create: ...
- modify: ...
- do-not-touch: ...
- verify-only: ...

验证锚点:
- {锚点}: {验证方式}

任务列表:
1. {任务名}
   文件: ...
   依赖: ...
   做什么: ...
   不做什么: ...
   完成条件: ...
   AI verify: ...

执行方式:
- {sequence / parallel / loop}
- 原因: ...

覆盖检查:
- {来源项}: {任务 / 锚点}

待定 / 风险:
- {不阻塞后续执行的风险；没有写 None}
```

规则：

- 不记录完整问答。
- 不记录被否掉的任务切法，除非用户要求。
- `任务列表` 是后续执行者的唯一执行入口。
- `AI verify` 不能为空。
- `待定 / 风险` 不能包含会影响任务目标、设计方向或验证标准的阻塞项。
- 只有完成本步骤展示和 handoff 写入，plan 才算完成。
