# implement

## Purpose

按可用任务输入修改代码，并记录实际执行计划、变更范围和执行结果。

只回答一件事：**代码是否已经按计划改完，并完成自动 / 人工质量闸口**。

不做：
- 不重新定义需求
- 不继续挖隐形需求
- 不重新设计接口 / 流程 / 数据
- 不重新规划完整任务
- 不静默扩大范围
- 不跳过已确认的验证锚点

## Steps

### 1. 读取可用任务输入

目标：确认 implement 有可执行输入。

步骤：

1. 读取可用上下文中的任务输入。可用上下文可能包括：
  - 用户原始描述
  - 已确认任务计划
  - 已确认执行规格
  - 文件清单
  - 验证锚点
  - do-not-touch 约束
  - 待定 / 风险
2. 提取：
  - 执行规格
  - 文件清单
  - 验证锚点
  - task 列表
  - 执行方式
  - do-not-touch
  - 待定 / 风险
3. 检查：
  - 有可用 task 列表 → 直接使用
  - 没有 task 列表，但目标、文件 / 区域范围、验证方式足够明确 → 在本阶段生成最小执行计划，继续执行
  - 缺少目标、文件 / 区域范围或验证方式 → 停止并输出阻塞项：缺少什么、为什么阻塞、需要补充什么
  - task 目标和已确认设计冲突 → 停止并输出设计冲突

展示模板：

```markdown
我会按计划执行这些任务：

| # | 任务 | 文件 / 区域 | AI verify |
|---|---|---|---|
| 1 | {任务名；没有计划时写“临时任务”} | {文件} | {验证方式} |
```

### 2. 选择执行能力

目标：为每个 task 选择执行能力档位，不绑定具体模型名。

能力档位：

| 档位 | 用途 |
|---|---|
| fast | 文档、配置、极小 patch |
| standard | 常规代码改动，范围清楚，验证明确 |
| high-reasoning | 跨模块、复杂调用链、状态 / 数据 / 兼容风险 |
| specialized | 需要特定工具能力，如 UI 自动化、浏览器、移动端、数据库等 |

步骤：

1. 根据 task 大小、风险、验证难度、是否需要特殊工具，给每个 task 选择能力档位。
2. 不写具体模型名；当前工具自行映射。
3. 如果当前工具不支持某档位，选择最接近档位，并记录。
4. 执行中允许升级档位，但必须记录原因。
5. 一般不在执行中降级；降级只能发生在 task / unit 开始前。

展示模板：

```markdown
执行能力选择：

| 任务 | 建议能力 | 原因 |
|---|---|---|
| Task 1 | standard | 单文件改动，验证明确 |
| Task 2 | high-reasoning | 跨模块调用链，涉及兼容 |
```

### 3. 判断执行粒度

目标：决定直接按 task 执行，还是把 task 拆成适合模型执行的 unit。

默认：

```text
Task = 执行单元
```

必须拆 unit 的情况：

| 规则 | 拆分方式 |
|---|---|
| 同一 task 同时包含实现和测试 | 拆成 `实现 unit` + `测试 unit` |
| 同一 task 同时包含新增逻辑和删除旧逻辑 | 拆成 `新增 / 接入 unit` + `清理 / 删除 unit` |
| 同一 task 涉及多个模块做同样动作 | 按模块拆 unit |
| 同一 task 涉及接口定义和调用方迁移 | 拆成 `接口 unit` + `调用方 unit` |
| 同一 task 涉及数据结构和 UI / 展示 | 拆成 `数据 unit` + `展示 unit` |
| 同一 task 涉及配置 / 开关和业务逻辑 | 拆成 `配置 unit` + `逻辑 unit` |
| 同一 task 涉及超过 3 个弱相关文件 | 按文件组拆 unit |
| task 的 AI verify 需要分阶段才能跑 | 按验证阶段拆 unit |

不拆 unit 的情况：

- 单文件小改
- 纯文档 / 配置
- 单一模块内同一动作
- 实现和验证都很明确
- 拆开后没有独立验证价值

步骤：

1. 对每个 task 套用拆分规则。
2. 未命中必须拆分规则 → 直接按 task 执行。
3. 命中规则 → 生成 unit。
4. 每个 unit 必须有：
  - 来源 task
  - 文件 / 区域
  - 做什么
  - 不做什么
  - 局部验证
  - 能力档位
5. 如果拆分后发现 task 边界不合理 → 停止并输出任务边界缺口。

展示模板：

```markdown
执行粒度判断：

| 任务 | 执行方式 | 原因 |
|---|---|---|
| Task 1 | 直接执行 | 单文件改动，验证明确 |
| Task 2 | 拆成 2 个执行单元 | 同时包含实现和测试 |
```

### 4. 设置人工检查点

目标：在模型继续做会增加偏离风险时，插入人工确认。

检查点类型：

| 类型 | 用途 |
|---|---|
| none | 不需要人工介入 |
| checkpoint | 继续前让用户确认方向是否对 |
| manual-verify | 自动验证不足，需要用户手动验收 |
| approval-required | 继续会扩大范围或改变计划，必须批准 |

默认：`none`。

必须设置 `checkpoint`：

| 触发条件 | 检查点位置 |
|---|---|
| 改用户可见行为 | 改完该 task / unit 后 |
| 改 UI / 交互 / 文案 | 截图或展示 diff 后 |
| 需要用户判断取舍 | 做决定前 |
| 当前任务输入中该项标记了非阻塞风险 | 做完相关 task / unit 后 |
| 自动验证无法覆盖核心效果 | 验证后，锁定结果前 |

必须设置 `approval-required`：

| 触发条件 | 处理 |
|---|---|
| 需要改已确认文件清单外的文件 | 先请求批准 |
| 需要新增依赖 | 先请求批准 |
| 需要改变接口 / 数据 / 流程 / 兼容策略 | 不在本阶段批准，停止并输出设计冲突 |
| 需要降低验证标准 | 先请求批准；如影响验收，停止并输出验证标准缺口 |
| 需要触碰 do-not-touch 文件 | 停止并输出范围 / 设计冲突 |
| 需要删除旧逻辑或迁移数据 | 若当前任务输入未明确授权，先请求批准 |

必须设置 `manual-verify`：

- 结果只能由用户人工确认
- 需要在外部系统 / 真实环境验证
- UI / 视觉效果无法自动截图验证
- 安全 / 权限 / 支付等高风险行为需要人工复核

允许 `none` 的条件：

- 不影响用户可见行为
- 不触碰高风险区域
- 不扩大文件范围
- 自动验证能覆盖核心结果
- 当前任务输入没有相关风险标记

步骤：

1. 对每个 task / unit 判断人工检查点类型。
2. 标记检查点原因。
3. `approval-required` 未获批准前，不继续执行。
4. `checkpoint` 在对应 task / unit 完成后暂停确认。
5. `manual-verify` 写入最终结果，不假装自动通过。

展示模板：

```markdown
人工检查点：

| 执行项 | 类型 | 原因 |
|---|---|---|
| Task 1 | none | 内部小改，有自动测试覆盖 |
| Unit 2.1 | checkpoint | 改用户可见行为，需要确认方向 |
| Unit 3.1 | approval-required | 需要扩大文件范围 |
```

### 5. 准备执行环境

目标：为 parallel 或隔离执行准备安全工作区。

worktree 是内部执行手段，不是交付信息。

需要临时 worktree 的情况：

- 已确认执行方式是 parallel
- 多个 task / unit 会同时修改不同文件
- 用户明确要求并行
- 需要隔离实验性实现
- 当前工作区有用户未提交改动，但当前任务可以在隔离目录执行

不需要临时 worktree 的情况：

- sequence 执行
- 单 task
- 并行任务最终会改同一文件
- 工具环境不支持 worktree
- 用户要求在当前目录直接改

步骤：

1. 判断是否需要临时 worktree。
2. 如果需要，按固定路径创建临时 worktree：
  - 根目录：`$SPRINT_DIR/worktrees`
  - 目录名：`{stage}-{task-or-unit-id}`，例如 `implement-task-1`、`implement-unit-2-1`
  - task / unit id 只允许小写字母、数字和 `-`；其他字符转成 `-`
3. 如果目标目录已存在：
  - 目录为空 → 复用
  - 目录非空 → 追加 `-{N}` 后缀，N 从 2 递增
4. 每个并行 task / unit 只能使用自己的临时 worktree。
5. 在临时 worktree 执行对应 task / unit。
6. 完成后合并回主工作区。
7. 合并成功后立即删除对应临时 worktree 目录。
8. handoff 不记录临时 worktree 路径、base commit、临时分支名、临时目录。
9. 合并失败时停止；保留冲突现场，只在最终结果中记录用户需要知道的阻塞原因。

用户展示模板：

```markdown
这部分适合隔离执行。我会用临时工作区完成并合并回当前工作区，成功后清理临时工作区。
```

### 6. 执行前检查

目标：防止 implement 一开始就污染工作区或偏离计划。

步骤：

1. 检查当前工作区状态。
2. 标记已有用户改动，不回滚、不覆盖。
3. 检查 task / unit 文件是否和 do-not-touch 冲突。
4. 检查依赖 task / unit 是否已完成。
5. 如果是 parallel 分支：
  - 只允许修改当前 task / unit 文件范围
  - 发现共享文件冲突 → 停止并输出并行策略冲突
6. 如果发现计划外但必须修改的文件：
  - 小偏差：记录后继续
  - 大偏差：停止并输出范围缺口
7. 如果存在 `approval-required` 且未获批准 → 停止等待用户。

展示模板：

```markdown
执行前检查：

- 工作区状态：{干净 / 有既有改动}
- 依赖：{满足 / 不满足}
- 文件边界：{符合 / 有冲突}
- 需要注意：
  - {用户已有改动 / do-not-touch / 并行冲突 / approval-required}
```

### 7. 按执行粒度实现

目标：严格按 task / unit 修改代码。

步骤：

1. 按已确认执行方式和 task / unit 依赖执行：
  - sequence：按顺序执行
  - parallel：每个分支只执行自己的范围
  - loop：本轮按 task / unit 执行，结果供循环判断
2. 每个 task / unit 执行：
  - 先读相关文件
  - 确认范围和不做事项
  - 修改代码
  - 不做计划外清理
  - 不扩大文件范围
3. 遇到冲突：
  - 实现细节不同但不改变 task 目标 → 记录偏离，继续
  - 需要改变接口 / 数据 / 流程 / 兼容策略 → 停止并输出设计冲突
  - 需要改变 task 边界 / 文件清单 / 验证方式 → 停止并输出执行计划缺口

展示模板：

```markdown
正在执行：

{Task / Unit}: {名称}
- 文件：{文件 / 区域}
- 做什么：{内容}
- 不做什么：{边界}
```

规则：

- 不改 do-not-touch 文件。
- 不修改 task / unit 范围外文件，除非按偏离规则处理。
- 不降低测试标准。
- 不把新发现的问题静默修掉。

### 8. 验证和结果汇总

目标：合并 task / unit 自检、锚点覆盖、人工检查和偏离检查，生成可审计结果。

步骤：

1. 执行 task / unit 的 AI verify 或局部验证。
2. 每个验证结果必须是：
  - pass
  - fail
  - not run + reason
  - manual required
3. 如果 fail：
  - 先在 task / unit 范围内修复
  - 同一 task / unit 最多尝试 2 轮
  - 仍失败则记录阻塞
4. 检查所有已确认验证锚点是否都有结果。
5. 检查人工检查点：
  - checkpoint 必须已被用户确认
  - approval-required 必须已获批准
  - manual-verify 必须写入结果；若阻塞则整体状态不能是完成
6. 检查偏离计划：
  - 是否改了计划外文件
  - 是否碰了 do-not-touch
  - 是否跳过 task / unit
  - 是否改变设计决定
  - 是否改变 task 边界
  - 是否降低验证标准
  - 是否新增依赖
  - 是否绕过人工检查点
7. 偏离分级：
  - 小偏离：不改变目标 / 设计 / 验证标准，记录后可继续
  - 大偏离：影响目标 / 设计 / task 边界 / 验证标准，停止并输出阻塞项
8. 汇总 task 状态：
  - done：task 直接完成，或其所有 unit 完成
  - partial：部分完成，或存在非阻塞 manual required / not run
  - blocked：关键验证失败、人工批准缺失、或存在未处理大偏离

展示模板：

```markdown
执行结果检查：

| 项目 | 结果 | 说明 |
|---|---|---|
| Task 1 | done | verify pass |
| Task 2 | partial | Unit 2.2 manual required |
| 锚点覆盖 | pass | ... |
| 偏离计划 | none / recorded / blocking | ... |
| 人工检查 | none / required / confirmed | ... |
```

### 9. 锁定实现结果

目标：给用户展示实现结果，并写入 handoff。

步骤：

1. 确认以下条件：
  - 所有 task 都有结果：done / partial / blocked
  - 拆了 unit 的 task 能由 unit 汇总出结果
  - 每个验证锚点都有结果
  - 人工检查点已处理
  - 所有偏离都已记录
  - 没有未处理的大偏离
  - 变更范围清楚可审计
2. 给用户展示结果。
3. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。
4. 如果 implement 是 loop 内最后挂载的实施 stage，写入 loop result：
  - `done`：所有 task 完成，且无阻塞验证失败 / 阻塞人工检查
  - `partial`：仍有遗留 task、阻塞、未完成验证或阻塞人工检查

展示模板：

```markdown
实现结果已记录 ✓

状态：{完成 / 部分完成 / 阻塞}

任务结果：
- {Task}: {done / partial / blocked}

验证：
- {验证项}: {结果}

人工检查：
- {检查项}: {结果}

偏离计划：
- {没有写“无”}

遗留 / 阻塞：
- {没有写“无”}
```

handoff 模板：

```markdown
执行计划:
- 能力档位: {Task / Unit: fast / standard / high-reasoning / specialized}
- 执行粒度: {Task 1 直接执行；Task 2 拆为 Unit 2.1 / Unit 2.2}
- 人工检查点: {Task / Unit: none / checkpoint / manual-verify / approval-required}

变更范围:
- 修改文件: {path}
- 计划外文件: {path；没有写 None}
- do-not-touch: {未触碰 / 触碰并阻塞}

执行结果:
- {Task}: {done / partial / blocked} — {说明}
- 验证: {AI verify / 局部验证 / 锚点}: {pass / fail / not run / manual required} — {说明}
- 偏离: {偏离；没有写 None}
- 人工检查: {checkpoint / manual-verify / approval-required}: {结果；没有写 None}
- 遗留 / 阻塞: {遗留或阻塞；没有写 None}
- Loop result: {done / partial；仅 loop 内最后实施 stage 需要}
```

规则：

- 不记录完整实现过程。
- 不记录无关代码阅读。
- 不记录临时 worktree 信息；成功则不留痕，失败才记录阻塞。
- 不隐藏失败验证。
- 不隐藏计划偏离。
- 不隐藏人工检查要求。
- 不把大偏离写成小偏离。
- `Loop result` 只在 implement 作为 loop 内最后实施 stage 时写。
- 只有完成本步骤展示和 handoff 写入，implement 才算完成。
