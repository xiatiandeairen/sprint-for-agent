# design

## Purpose

把已对齐的目标和探索结果，收敛成可验证、可供 plan 使用的设计契约。

只回答一件事：**这件事准备怎么做，哪些设计决定已经锁定**。

不做：
- 不重新定义需求
- 不继续挖隐形需求
- 不拆执行任务
- 不写代码
- 不生成完整架构文档

## Steps

### 1. 判断是否需要设计

目标：判断当前任务是否需要单独设计。

步骤：

1. 读取 clarify / explore 的 handoff；如果没有，就使用用户原始描述。
2. 检查是否命中以下信号：
  - 跨多个模块或层级
  - 涉及接口、数据结构、协议变化
  - 涉及流程、状态、权限、错误处理变化
  - 有兼容性、迁移、回滚风险
  - 存在多种合理实现路径
  - 后续 plan 无法直接拆任务
3. 判定：
  - 没有明显信号 → 进入 §10，记录“无需单独设计”
  - 有信号 → 进入 §2

不向用户展示内部判断表。

### 2. 判断是否需要读代码

目标：决定是否需要基于代码现状设计。

需要读代码的情况：

- 设计会改现有模块边界
- 涉及已有接口、数据结构、状态流
- 需要兼容旧逻辑
- 需要知道现有调用关系
- 用户要求“基于当前实现”
- 不读代码会导致方案可能不可落地

不需要读代码的情况：

- 新增独立文件 / 文档 / 配置
- 纯规则或流程设计
- 用户只要概念方案
- 当前阶段只是确定方向，不需要实现细节

读代码方式：

1. 先定位入口，不全库浏览。
2. 只读和设计对象相关的文件。
3. 每次读代码都要回答一个明确问题，例如：
  - 当前调用链是什么
  - 数据从哪里来，到哪里去
  - 现有接口能否复用
  - 哪些文件不能碰
4. 读完只输出“现状约束”，不输出代码摘抄。

用户展示模板：

```markdown
我需要先看少量代码来确认设计是否落地，重点看：

- 当前入口：{入口}
- 相关调用：{调用关系}
- 数据结构：{数据对象}

目的：确认方案不会和现有实现冲突。
```

### 3. 判断是否需要 web search

目标：决定是否需要外部依据。

需要 web search 的情况：

- 涉及第三方 API / SDK / 框架能力
- 涉及近期变化的库、规范、平台限制
- 涉及安全、合规、浏览器 / 系统行为
- 用户问“业界怎么做”
- 设计依赖外部约束，不查会猜错

不需要 web search 的情况：

- 完全是项目内部设计
- 只是整理现有需求
- 外部事实不会影响方案选择

web search 方式：

1. 只查和设计决策有关的问题。
2. 优先官方文档、标准、源码、RFC。
3. 搜索结果必须转成设计约束。
4. 不把搜索摘要当成设计本身。

用户展示模板：

```markdown
这里有外部约束会影响设计，我会查官方资料确认：

- {问题 1}
- {问题 2}

查完只保留会影响本次设计的约束。
```

### 4. 确定设计对象

目标：明确这次真正需要设计哪些东西，避免全量架构化。

设计对象来源：

- clarify 的目标契约
- explore 的本期补充
- 代码现状约束
- 外部约束
- 用户明确边界

步骤：

1. 根据已知依据列出 1-5 个设计对象。
2. 每个设计对象必须是后续实现会依赖的东西。
3. 用户可以确认、删掉、补充。

展示模板：

```markdown
这次不需要完整架构设计，但有几个点需要先定下来：

| 要定什么 | 为什么要定 | 依据 |
|---|---|---|
| {设计对象} | {不定会卡在哪里} | 需求 / 代码现状 / 外部约束 |

请确认：
- 保留这些点
- 删掉某项
- 补充某项
```

设计对象类型：

- 改动边界：改哪里，不改哪里
- 调用关系：谁调用谁
- 数据形状：字段、结构、状态
- 流程顺序：先后步骤、分支
- 兼容策略：新旧逻辑如何共存
- 错误处理：失败时怎么表现
- 配置 / 开关：是否需要可控入口
- 验证方式：怎么证明设计可行

### 5. 选择实现路径

目标：如果存在多种合理做法，让用户决定采用哪条路径。

步骤：

1. 判断是否只有一种显然做法。
2. 如果只有一种：
  - 简短说明原因
  - 进入 §6
3. 如果有多种：
  - 给 2-3 个候选路径
  - 每个路径说明适合什么、代价是什么、依据是什么
  - 推荐一个，但用户拍板

展示模板：

```markdown
这里有几种做法，需要先选方向：

| 路径 | 适合情况 | 代价 / 风险 | 依据 |
|---|---|---|---|
| {路径 A} | {适合什么} | {主要成本或风险} | 需求 / 代码现状 / 外部约束 |
| {路径 B} | {适合什么} | {主要成本或风险} | ... |

我建议选 {编号}，因为 {一句话理由}。

回复：选 1/2/3，或直接改写。
```

规则：

- 不超过 3 个路径。
- 不制造陪跑项。
- 不把路径写成具体任务列表。
- 如果路径差异只是不重要的实现细节，不展示给用户。

### 6. 生成可视化设计草案

目标：把已选路径展开成用户能确认的设计草案。

步骤：

1. 只生成被 §4 触发的设计维度。
2. 用问题导向表达，不堆专业字段。
3. 每一项都要能被后续 plan 消费。
4. 如果某项仍不确定，标为“待确认”。
5. 按场景选择图表：
  - 流程变化 → Mermaid flowchart
  - 调用关系 → Mermaid sequence diagram
  - 状态变化 → Mermaid state diagram
  - 模块边界 → Mermaid graph
  - 数据结构 → 表格
  - 权限 / 决策规则 → 决策表
  - 兼容 / 迁移 → Before / After 表

展示模板：

```markdown
基于当前方向，我建议这样设计：

{图表或表格}

关键点：

- 要改哪里：
  - {改动对象}

- 不改哪里：
  - {明确边界}

- 怎么流转：
  - {主要步骤 / 分支}

- 谁和谁交互：
  - {调用关系 / 输入输出}

- 数据怎么变：
  - {字段 / 状态 / 配置变化}

- 失败时怎么办：
  - {错误处理 / 回退}

- 怎样证明设计可行：
  - {验证方式}

还需要确认：
1. {会影响实现方向的问题}
2. {会影响兼容 / 风险的问题}
```

规则：

- 没触发的维度不展示。
- 不写“暂无”凑字段。
- 设计草案不拆任务。
- 用户修正后最多跟进 1 轮。

### 7. 结构化验证需求支撑

目标：不用“我觉得可以”，而是逐条验证设计能否支撑需求。

步骤：

1. 从 clarify 的做好标准和 explore 的本期补充提取检查项。
2. 每个做好标准至少对应一行。
3. 对每一行说明：
  - 设计如何支撑
  - 后续怎么验证
  - 当前结论
4. 出现“不支撑”不能进入 §8。
5. 出现“部分支撑”时，让用户决定：
  - 调整设计
  - 降低本期范围
  - 记录风险但继续

展示模板：

```markdown
我用需求反推检查了一遍：

| 需求 / 做好标准 | 设计如何支撑 | 后续怎么验证 | 结论 |
|---|---|---|---|
| {需求点} | {对应设计点} | {测试 / 构建 / 手动验证 / 静态检查} | 支撑 / 部分支撑 / 不支撑 |
```

规则：

- 每个做好标准至少有一行。
- explore 加入本期的补充也要验证。
- `不支撑` 必须回到 §6 调整设计，或回到 clarify / explore 调整范围。
- `部分支撑` 必须写清楚缺口，并由用户确认处理方式。

### 8. 设计覆盖检查

目标：证明设计已经覆盖需求链路中会影响实现的所有关键点。

需求链路：

```text
需求目标
→ 用户 / 触发场景
→ 输入
→ 处理流程
→ 状态 / 数据变化
→ 输出 / 用户可见结果
→ 错误 / 边界情况
→ 验证方式
```

步骤：

1. 按需求链路逐项检查是否涉及。
2. `是否涉及 = 否` 时，写一句理由。
3. `是否涉及 = 是` 时，必须已有设计覆盖。
4. 任一涉及项未覆盖，不能进入 §9。
5. 如果用户决定不覆盖，必须转成明确的范围削减或风险记录。

展示模板：

```markdown
设计覆盖检查：

| 链路环节 | 是否涉及 | 当前设计是否覆盖 | 缺口 |
|---|---|---|---|
| 触发入口 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 输入 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 处理流程 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 状态 / 数据 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 输出结果 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 错误 / 边界 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 兼容 / 迁移 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
| 验证方式 | 是 / 否 | 已覆盖 / 未覆盖 | {缺口或理由} |
```

完成标准：

- 需求链路中所有“涉及”的环节都已覆盖。
- plan 阶段可以只拆任务和安排执行，不需要重新决定方案、接口、数据、流程、兼容策略。

### 9. 设计决定检查

目标：锁定会影响实现的关键决定，避免 plan 阶段重新猜。

步骤：

1. 从设计草案、需求支撑验证、覆盖检查中提取关键决定。
2. 每条决定必须满足至少一个条件：
  - 会影响文件边界
  - 会影响接口或数据结构
  - 会影响兼容性
  - 会影响错误处理
  - 会影响验证方式
3. 用户确认每条决定。
4. 未确认但不阻塞的项写入“待定 / 风险”。
5. 阻塞性决定未确认时，停止等待用户。

展示模板：

```markdown
进入计划前，需要锁定这些决定：

| 决定 | 为什么重要 | 依据 | 请确认 |
|---|---|---|---|
| {决定} | {影响实现的原因} | 需求 / 代码 / 外部约束 / 验证表 | 对 / 不对 / 待定 |
```

规则：

- 最多 6 条。
- 不写纯描述性结论。
- “待定”只能用于不阻塞 plan 的细节。
- 阻塞项不能待定。

### 10. 锁定设计结果

目标：给用户展示最终设计摘要，并写入 handoff。

步骤：

1. 确认以下条件都成立：
  - 已判断是否需要单独设计
  - 无需单独设计时，已写清楚原因，且 plan 可以直接拆任务
  - 需要设计时，设计对象已确认
  - 需要读代码时，代码现状已转成设计约束
  - 需要 web search 时，外部资料已转成设计约束
  - 需要选择路径时，路径已确认
  - 需要设计时，每个做好标准都有对应设计点和验证方式
  - 需要设计时，需求链路中所有涉及环节都已覆盖
  - 需要设计时，阻塞性设计决定已确认
  - 待定项均不阻塞 plan
2. 给用户展示最终设计摘要。
3. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。

展示模板：

```markdown
设计结果已确认 ✓

设计方向：
{一句话}

这次会怎么做：
- {关键设计点}

明确不做：
- {边界}

需要 plan 注意：
- {拆任务时必须考虑的约束 / 风险}
```

handoff 模板：

```markdown
设计结论:
{一句话说明采用的设计方向；无需设计时写“无需单独设计，原因：...”}

设计依据:
- 代码现状: {影响设计的代码约束；没有写 None}
- 外部约束: {影响设计的外部约束；没有写 None}

设计契约:
- 改动对象: {要改哪里}
- 边界: {不改哪里}
- 流程: {主要流程；不涉及写 None}
- 接口 / 数据: {接口、字段、状态、配置变化；不涉及写 None}
- 错误 / 回退: {失败处理；不涉及写 None}
- 验证: {证明设计可行的方式}

需求支撑检查:
- {需求点}: {支撑方式} — {验证方式}

Plan 不应重新讨论:
- {已确认设计决定；没有写 None}

给 plan 的提示:
- {文件边界、拆分方向、验证重点；没有写 None}

待定 / 风险:
- {不阻塞 plan 但需要注意的内容；没有写 None}
```

规则：

- 不记录内部设计判断表。
- 不记录完整问答。
- 不记录被否掉的路径，除非用户要求保留。
- `设计契约` 必须能被 plan 直接使用。
- `待定 / 风险` 不能包含阻塞性决定。
- `Plan 不应重新讨论` 必须覆盖会影响方案、接口、数据、流程、兼容策略的已确认决定。
- 只有完成本步骤展示和 handoff 写入，design 才算完成。
