# verify

## Purpose

独立验证当前变更是否满足已确认的验证锚点、成功标准和基础质量要求。

只回答一件事：**当前结果能不能可信地结束**。

不做：
- 不改代码
- 不做代码评审
- 不重新设计
- 不重新拆任务
- 不替用户确认人工验收项

## Steps

### 1. 读取可用验证上下文

目标：确认 verify 有足够信息判断当前结果。

步骤：

1. 读取可用上下文。可用上下文可能包括：
  - 用户原始目标
  - 已确认成功标准
  - 已确认验证锚点
  - 当前代码改动
  - 已有执行结果
  - 测试 / build / lint / typecheck 命令
  - 人工验收项
  - 风险 / 阻塞记录
2. 如果没有明确验证锚点，但有当前代码改动和目标，则基于 diff 和项目结构生成最小验证计划。
3. 如果缺少目标、代码改动或可验证方式，停止并输出阻塞项：缺少什么、为什么阻塞、需要补充什么。

展示模板：

```markdown
我会验证这些内容：

- 目标 / 成功标准：{摘要}
- 验证锚点：{锚点}
- 机械验证：{测试 / build / lint / typecheck}
- 人工验收：{需要人工确认的项；没有写“无”}
```

### 2. 确定验证范围

目标：明确要验证什么，以及哪些不验证。

步骤：

1. 根据可用上下文和当前 diff 确定：
  - 变更文件
  - 受影响模块
  - 需要跑的命令
  - 需要检查的锚点
  - 需要人工验证的项
2. 如果某项不验证，必须写明原因。
3. 不把“未验证”写成通过。

展示模板：

```markdown
验证范围：

| 项目 | 验证方式 | 说明 |
|---|---|---|
| {变更 / 锚点} | {命令 / 静态检查 / 人工验收} | {说明} |
```

### 3. 执行机械验证

目标：执行可自动完成的验证命令和静态检查。

步骤：

1. 执行验证命令，例如：
  - test
  - build
  - lint
  - typecheck
  - 文件存在 / 内容检查
2. 每个结果必须是：
  - pass
  - fail
  - not run + reason
3. 失败时不修代码，只记录失败信息和阻塞影响。
4. 命令不存在或环境缺失时，记录 `not run + reason`。

展示模板：

```markdown
机械验证：

| 验证项 | 结果 | 说明 |
|---|---|---|
| {命令 / 检查} | pass / fail / not run | {说明} |
```

### 4. 覆盖与范围检查

目标：确认验证覆盖成功标准，并且当前变更没有明显越界。

步骤：

1. 检查每个成功标准 / 验证锚点是否有结果。
2. 检查当前变更范围：
  - 是否有计划外文件
  - 是否触碰 do-not-touch
  - 是否存在未记录变更
3. 检查结果写入验证结果；不单独扩大 handoff 结构。
4. 未覆盖的成功标准不能算 pass。

展示模板：

```markdown
覆盖与范围检查：

| 检查项 | 结果 | 说明 |
|---|---|---|
| {成功标准 / 锚点 / 范围项} | pass / fail / not run / manual required | {说明} |
```

### 5. 人工验收检查

目标：明确哪些结果必须由用户或外部环境确认。

步骤：

1. 汇总 manual-verify / 人工验收项。
2. 每项结果必须是：
  - confirmed
  - required
  - not required
3. 未确认的阻塞人工验收项不能算 pass；输出后暂停，等待用户回复。
4. 不替用户确认主观效果、外部系统结果、真实环境行为。

展示模板：

```markdown
人工验收：

| 项目 | 状态 | 说明 |
|---|---|---|
| {验收项} | confirmed / required / not required | {说明} |
```

### 6. 锁定验证结果

目标：给用户展示验证结论，并写入 handoff。

结果判定：

- `pass`：所有阻塞验证通过，且无阻塞人工验收。
- `fail`：任一阻塞验证失败、未跑且阻塞、或人工验收阻塞。
- `partial`：机械验证通过，但仍有非阻塞 not run / manual required / 风险。

步骤：

1. 汇总机械验证、覆盖检查、范围检查、人工验收。
2. 判定 pass / fail / partial。
3. 给用户展示最终结果。
4. 按本步骤的 handoff 模板生成 `append_stage` operation 的 `{BODY}`。
5. 如果 verify 是 loop 终点，写入 loop result：
  - `pass`：全部阻塞验证通过，跳出循环
  - `fail`：存在阻塞验证失败、阻塞未跑或阻塞人工验收

展示模板：

```markdown
验证结果已记录 ✓

状态：{pass / fail / partial}

验证：
- {验证项}: {结果}

人工验收：
- {验收项}: {状态}

遗留 / 阻塞：
- {没有写“无”}
```

handoff 模板：

```markdown
验证结论:
{pass / fail / partial，一句话说明}
{Loop result: pass / fail；仅 loop 终点需要}

验证结果:
- {命令 / 锚点 / 范围检查}: {pass / fail / not run / manual required} — {说明}

人工验收:
- {项目}: {required / confirmed / not required} — {说明}

遗留 / 阻塞:
- {遗留或阻塞；没有写 None}
```

规则：

- 不记录完整命令输出，只记录关键失败信息。
- 不把未运行写成通过。
- 不把人工验收写成自动通过。
- 不修代码。
- `Loop result` 只在 verify 作为 loop 终点时写。
- 只有完成本步骤展示和 handoff 写入，verify 才算完成。
