# Sprint for Analysis

## 1. 目标与边界

形成可用于理解、判断或决策的结论，并说明证据、推理桥梁、替代解释、限制和下一步。

基本关系：

```text
输入 + 可用材料
→ 识别分析形态与问题
→ 收集最小充分证据
→ 分析 ⇄ 反证
→ 证据门禁
→ 结论或建议
```

这不是固定 stage。问题和材料已经清楚时直接分析，不确认内部流程，不为形式创建 handoff。

不接受：

- 主要产出是代码改动、PR 代码审查或度量驱动代码优化的任务
- 用户已给出明确动作、无需判断的纯执行
- 重点是文风而非事实或判断的创作

按主要产出处理交叉场景：

- 只调查软件问题的原因、不修改仓库时属于本 skill；诊断并修复时使用 `sprint-for-code`。
- 需求、报告、论证或事故文档审阅属于本 skill；PR、diff 或实现代码审查使用 `sprint-for-code`。
- 简单事实问答、摘要、翻译、改写、头脑风暴和无需判断的执行不属于本 skill。

分析后需要执行时，只在原请求已授权且属于当前能力范围时继续；否则给出可执行下一步，不把建议写成已执行。

## 2. Hard Rules

### 2.1 宿主与授权

- 遵守宿主的 system / developer / safety / sandbox / browsing / approval 规则。
- 只分析用户授权的问题；不把相邻问题静默纳入核心结论。
- 用户控制问题、边界、价值权重和重大取舍；分析方法、材料定位和普通判断细节由 AI 自主决定。

### 2.2 证据真实性

- 区分事实、推断和建议；不要把猜测写成事实。
- 让每个关键结论都能追溯到证据或明确前提。
- 查找会改变结论的反证、替代解释和失败条件，不为显得谨慎而机械反对一切。
- 材料不足、相互冲突或不可验证时，缩小结论范围或输出无法判断。
- 不用主观 `high / medium / low` 代替证据；仅在不确定性会影响决策时说明校准后的置信度及原因。

### 2.3 范围与材料

- 优先使用用户材料和原始来源；必要时再扩展到代码、日志、Git 历史或外部资料。
- 读取授权范围内的只读材料不需要逐项批准。
- 记录来源、时效、样本、口径和适用范围；不要把大量原文搬入结果。
- 当前事实可能变化或外部约束影响结论时，按宿主规则查询并优先使用官方或一手来源。
- 范围外发现作为后续机会报告，不改变本次核心问题。

### 2.4 用户交互

只有以下情况需要暂停询问用户：

1. 缺失答案会导向实质不同的分析问题或结论。
2. 需要扩大问题、对象、时间范围或材料权限。
3. 判断依赖无法从上下文推断的价值权重或决策标准。
4. 用户必须在“补证、接受有限结论、调整问题”之间选择。

不要因为以下事项询问用户：

- 选择普通分析框架或表达结构。
- 读取范围内文件、日志、代码或 Git 历史。
- 查找支持证据、反证和替代解释。
- 将材料整理成证据、比较维度或因果假设。
- 在目标和标准明确时给出推荐。

询问时说明：缺什么、为什么重要、候选项的影响和推荐默认项。发出选择、授权或确认请求后结束当前回合；得到回复前不继续依赖该答案的分析。

## 3. 分析形态

先判断用户最终需要哪种结论。形态决定分析循环，不限制领域。

### 3.1 investigate

查明发生了什么、为什么发生、证据支持哪种解释。

适用：调查、根因分析、日志或数据解读、研究综合、现状诊断。

```text
问题 → 证据 → 假设 ⇄ 检验与反证 → 最佳支持解释
```

### 3.2 decide

比较可选路径并给出推荐或决策条件。

适用：方案比较、技术选型、需求取舍、风险决策、策略建议、决策备忘录。

```text
目标与标准 → 选项 → 证据与 trade-off ⇄ 反证 → 推荐
```

### 3.3 review

依据标准审视主张、材料或分析是否成立。

适用：文档审阅、事故报告审视、论证检查、需求质量 review、证据充分性评估。

```text
主张与标准 → 检查证据 ⇄ 挑战 → verdict
```

“调查后决定”可先 investigate 再 decide；“审阅后补充调查”可从 finding 派生 investigate。复用已解决问题，不重复走完整流程。

## 4. 问题系统

问题组是候选问题和覆盖检查，不是固定问卷。短任务只在当前上下文维护问题状态。

### 4.1 从输入提取

识别：

- 核心问题与期望结论
- 使用场景和决策主体
- 已知事实、主张和用户假设
- 对象、时间、地域、系统或业务范围
- 判断标准、价值偏好和硬约束
- 可用材料、已有证据和明确未知项

直接复用输入已经可靠回答的内容，不重复确认。

### 4.2 选择问题

只有同时满足以下条件的问题才进入当前分析：

```text
与核心问题相关
AND 尚未被输入或证据可靠回答
AND 不回答可能实质影响解释、比较、推荐或 verdict
```

对每个候选问题判断：

1. 它服务哪个结论或决定？
2. 现有材料已经回答了吗？
3. 不同答案会改变什么？
4. 能从哪里取得答案？
5. 不知道时能否输出受限结论？

### 4.3 解决顺序

优先从以下来源获得答案：

1. 用户输入和已提供材料
2. 当前项目或业务上下文
3. 原始数据、日志、文档、代码或 Git 历史
4. 官方资料、标准、论文或其他一手外部来源
5. 可复现计算、查询或最小实验
6. 明确标注且不改变核心结论的假设
7. 用户决定

能调查的问题不要转嫁给用户。来源选择会显著影响结论时，说明取舍；只有涉及权限、范围或价值标准才要求用户决定。

### 4.4 问题状态

按需在内部记录：

- `answered`：已有可靠答案
- `investigate`：需要补材料、查询或计算
- `assumed`：基于明确假设继续
- `user-decision`：必须由用户决定
- `blocked`：当前无法可靠回答
- `invalidated`：上游事实或口径变化，原答案失效

### 4.5 动态问题

准备形成解释、比较、推荐或 verdict 时，如果依据不足，且不同答案可能实质改变结果，就生成动态问题。

动态问题必须能说明：

- 它保护哪个结论、标准、证据链或风险？
- 为什么现有问题不能覆盖？
- 答案从哪里获得？
- 不回答会如何限制结论？
- 是否改变分析范围或价值口径？

不能追溯到核心问题或决策的问题不得加入；仅为了“更完整”不得无限收集。

### 4.6 局部失效

- 只影响某条证据：重评依赖该证据的结论。
- 影响口径或比较维度：重算受影响比较，不重做无关部分。
- 影响核心假设：使依赖它的解释或推荐失效，并检验替代假设。
- 影响问题、范围或价值权重：请求用户决定。

## 5. 核心问题组

### 5.1 定义问题

- 用户真正要理解、判断或选择什么？
- 结论用于决策、汇报、排查还是学习？
- 对象、时间和边界是什么？
- 怎样的结论才有用？
- 哪些标准或价值权重会改变答案？
- 哪些缺口会导向实质不同的问题？

问题已清楚时直接继续。非阻塞缺口作为假设或限制记录。

### 5.2 建立证据

- 需要证明或否定哪些关键主张？
- 有哪些直接证据、间接证据和反证？
- 来源是否可靠、独立、及时并适用于当前范围？
- 样本、口径、选择偏差和缺失数据是什么？
- 哪些事实仍然未知？未知会影响哪条结论？

按需维护最小证据映射：

| 主张 | 证据 | 支持/反对 | 可靠性依据 | 时效与范围 |
|---|---|---|---|---|
| {待判断主张} | {来源/计算} | {方向} | {为什么可信} | {适用条件} |

### 5.3 选择分析结构

- 需要解释因果、比较选项、审查主张还是识别模式？
- 哪些维度直接服务核心问题？
- 哪些是假设，怎样被证伪？
- 判断维度是否重叠、遗漏或暗含价值权重？
- 是否存在更简单且同样有效的结构？

框架是内部工具，不为形式展示。只有维度或权重体现用户价值取舍时才请求用户决定。

### 5.4 形成分析

- 证据实际显示什么？
- 从观察到结论的推理桥梁是什么？
- 哪些关系是因果、相关、共同约束或纯巧合？
- 哪个解释或选项获得最多直接支持？
- 冲突证据怎样处理？
- 结论在什么条件下成立或失效？

在输出中按重要性区分事实、推断和建议，不强制所有内容套表格。

### 5.5 挑战结论

- 有什么相反证据或替代解释？
- 是否把相关性写成因果？
- 是否存在样本、选择、幸存者、时效或口径偏差？
- 哪个未验证前提承载了结论？
- 如果建议错误，最可能错在哪里，代价是什么？
- 什么新证据会让结论改变？

优先挑战会影响推荐、风险或行动的结论；不要为每个常识性事实制造形式化反证。

### 5.6 证据门禁

- 核心问题是否被直接回答？
- 每个关键结论是否有可追溯证据和推理桥梁？
- 重要反证和替代解释是否已处理？
- 结论是否超出材料的对象、时间、样本或口径？
- 哪些内容仍是条件性判断或无法判断？
- 当前证据足以支持理解、推荐还是仅支持下一步取证？

通用证据状态：

- `supported`：证据足以支持声明范围内的结论。
- `limited`：结论有用，但依赖明确条件、假设或证据限制。
- `inconclusive`：无法可靠回答核心问题，只能说明缺口和下一步取证。

## 6. 分析循环

### 6.1 investigate

1. 把现象或问题转成可检验假设。
2. 收集能区分假设的最小充分证据，不堆积无关材料。
3. 比较各假设对现有事实的解释力。
4. 主动寻找反例、时间顺序和替代原因。
5. 根据新证据更新、合并或淘汰假设。
6. 输出最佳支持解释、适用条件和仍缺证据。

没有直接因果证据时写“最可能解释”而非“根因已证明”。

### 6.2 decide

1. 明确目标、硬约束和真正影响选择的标准。
2. 识别可行选项，包括保持现状；不制造明显陪跑项。
3. 为每个关键维度收集可比证据，避免不同口径比较。
4. 区分事实 trade-off 与价值权重。
5. 检查推荐在什么场景下会反转。
6. 给出推荐、原因、不选其他方案的理由和改变建议所需的新证据。

目标和权重明确时直接推荐；证据不足时给条件式建议，不把列选项当作完成。

### 6.3 review

1. 明确被审对象、核心主张、目标读者和判断标准。
2. 检查主张是否有证据，证据是否真的支持主张。
3. 找出事实错误、逻辑跳跃、歧义、遗漏和不当确定性。
4. 尝试用反证、边界案例或替代解释挑战关键主张。
5. 只报告会影响理解、判断或行动的问题，不把纯风格偏好写成缺陷。
6. 给出 verdict、问题影响和修改方向；默认不直接改原材料。

用户明确要求“review 并修改”时，可在 verdict 后执行已授权修改。

## 7. 领域问题包

按任务信号激活，只回答会影响结论的问题。

### 7.1 root-cause

- 现象、基线、变化时间和影响范围是什么？
- 直接触发、必要条件、促成因素和系统性原因分别是什么？
- 时间顺序和机制证据是否支持因果？
- 哪些替代原因能解释同一现象？
- 什么验证能区分候选原因？

### 7.2 comparison

- 目标、硬约束、选项和比较基准是否一致？
- 哪些维度是事实差异，哪些取决于价值权重？
- 总成本、切换成本、可逆性和机会成本是什么？
- 推荐在什么条件下会改变？

### 7.3 research

- 问题需要事实地图、趋势解释还是可行路径？
- 哪些信息具有时效性，哪些来源是一手或权威？
- 不同来源是否独立，术语和统计口径是否一致？
- 当前证据反映全局还是局部样本？

### 7.4 requirements

- 用户目标和待解决问题是什么，而不是已给方案是什么？
- 哪些是必须有、可以后做和明确不做？
- 利益相关者、约束、边界和验收信号是什么？
- 需求之间是否冲突，优先级依据是什么？
- 哪些隐含假设尚未验证？

### 7.5 data-and-logs

- 指标定义、分母、时间窗、时区和样本选择是什么？
- 数据是否完整、重复、延迟或受埋点变化影响？
- 变化来自真实行为、口径、季节性还是数据质量？
- 相关模式能否支持因果，是否需要对照或分群？

### 7.6 document-and-claim-review

- 核心主张、证据和推理桥梁是否明确？
- 事实是否准确、及时并可追溯？
- 是否遗漏关键反例、边界、风险或读者需要的信息？
- 语言确定性是否超过证据强度？

### 7.7 risk

- 风险事件、触发条件、概率依据和影响是什么？
- 风险是否可检测、可逆、可缓解或可转移？
- 最坏情况、尾部风险和相关风险是否被忽略？
- 缓解措施本身带来什么成本和新风险？

### 7.8 strategy

- 目标、资源、约束、时间尺度和成功信号是什么？
- 现状问题来自定位、能力、执行还是外部变化？
- 哪些选择具有杠杆效应、依赖或不可逆性？
- 建议基于哪些假设，最先验证哪个假设？

其他领域按动态问题规则派生，不为每个行业建立固定流程。

## 8. 结论与汇报

先给答案，再给支撑答案所需的最小结构。

### 8.1 investigate

结论：`best-supported / plausible / inconclusive`

汇报：最佳支持解释、关键证据、推理桥梁、替代解释、限制和下一步取证。

### 8.2 decide

结论：`recommended / conditional / insufficient-evidence`

汇报：推荐、决定性标准、关键 trade-off、不选其他方案的理由、风险和建议反转条件。

### 8.3 review

结论：`supported / needs-revision / unsupported / inconclusive`

汇报：verdict、按影响排序的问题、证据、修改方向、检查范围和限制。

按任务需要引用来源；不要输出完整内部问题账本、固定 stage、材料搬运、工具流水账或无决策价值的过程复述。

## 9. 可选持久化

仅在用户明确要求、任务需要跨会话、材料规模大或分析可能中断时保存状态。优先使用宿主原生任务、计划或恢复能力。

最小持久化内容：

- 核心问题、范围和使用场景
- 分析形态与判断标准
- 已确认事实、假设和证据映射
- 未解决问题、反证、限制和当前结论
- 下一步

不维护固定 sequence、stage cursor、循环轮次、人工章节序号或每阶段耗时。

## 10. 完成定义

结束前确保：

- 回答用户真正的问题，而不是只展示分析过程。
- 关键结论有证据和可检查的推理桥梁。
- 重要反证、替代解释和限制没有被隐藏。
- 结论强度没有超过证据范围。
- 输出使用与分析形态匹配的 verdict，并给出可行动的下一步。
