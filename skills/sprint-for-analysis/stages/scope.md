# scope

## Purpose

把模糊分析请求转成可回答的问题，并锁定分析边界、成功标准和排除项。

只回答一件事：**本次分析到底回答什么，不回答什么，结果将如何被使用**。

不做：
- 不收集新证据
- 不选择复杂框架
- 不给分析结论
- 不扩大问题

## Steps

### 0. 用户提示和门禁

进入本 stage 时告诉用户：先锁定问题和范围，避免后续分析发散。

必须停下来等用户的情况；触发时输出后暂停，等待用户回复：
- 核心问题、使用场景或判断标准不清，且会影响后续结论
- 时间范围、对象范围、比较对象、排除项不清，且会改变分析边界
- 材料不足，用户需要选择“补材料 / 继续有限分析 / 缩小问题”
- 发现 scope 外但有价值的问题，用户需要决定是否记录后续或变更本期范围

### 1. 判断是否需要澄清

需要澄清的信号：
- 问题不是问句，也没有明确判断对象
- 不知道结论用于决策、汇报、排查还是学习
- 成功标准、时间范围、对象范围或比较对象不清
- 用户给的是材料，但没说要分析什么

不需要澄清的情况：
- 一句话能明确核心问题、用途和期望输出
- 缺口不影响后续分析，只影响呈现形式

需要澄清时，一次最多问 3 个问题，优先级：
1. 你要回答的核心问题是什么？
2. 这个结论用于什么决策或动作？
3. 范围、时间、对象或口径是否有硬边界？

### 2. 形成问题契约

从用户原始描述和澄清结果中提取：
- 核心问题
- 使用场景
- 判断标准
- 可用材料
- 时间 / 对象 / 地域 / 系统 / 业务范围
- 明确排除项

### 3. 定义分析范围

范围必须包含：
- In scope：本次必须覆盖的问题或对象
- Out of scope：不分析的相邻问题
- Success：什么样的输出算有用
- Decision owner：如果用户未说明，写 `user`

### 4. 输出范围契约

输出后必须向用户展示问题契约和范围契约；输出后暂停，等待用户回复；用户确认后才能进入后续 stage。

handoff 模板：

```markdown
问题契约:
- 核心问题: {一句话}
- 使用场景: {决策 / 汇报 / 排查 / 学习 / 其他}
- 判断标准: {用户给出的标准；没有写 None}
- 已知边界: {时间 / 对象 / 材料 / 排除项；没有写 None}
- 待确认但不阻塞: {不影响继续分析的缺口；没有写 None}

范围契约:
- 本次回答: {1-3 条}
- 本次不回答: {1-5 条；没有写 None}
- 成功标准: {可判断的交付标准}
- 可用材料: {文件 / 数据 / 页面 / 口述信息；没有写 None}
- 需要外部资料: {yes/no + 原因}
- 主要限制: {当前已知限制；没有写 None}
```
